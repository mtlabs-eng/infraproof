# InfraProof project instructions

## Mission

InfraProof is an offline-first verifier for Terraform and OpenTofu changes generated by humans or coding agents. It compares declared intent with a Terraform plan, evaluates deterministic policies, and produces traceable evidence before infrastructure is changed.

## Non-negotiable safety rules

- Never execute `terraform apply`, `terraform destroy`, or an equivalent mutation.
- Never request, read, store, print, or transmit cloud credentials.
- Never upload source code, state, plans, or evidence to an external service.
- Treat Terraform plan and state data as potentially sensitive.
- Redact values marked sensitive before logging, rendering, or returning errors.
- Preserve unknown values as unknown. Never infer or invent them.
- A `BLOCK` decision must be supported by deterministic evidence.
- An LLM result may explain or propose, but must never be the sole reason for `BLOCK`.
- Work only on the explicitly active milestone.

## Engineering rules

- Use Go unless an approved milestone says otherwise.
- Keep the core independent of AWS, Azure, GCP, MCP, GitHub, and any LLM vendor.
- Put provider-specific interpretation behind mapper interfaces.
- Normalize provider resources into common capabilities only where semantics are genuinely equivalent.
- Represent unsupported or ambiguous semantics explicitly; do not force them into a common model.
- Validate data at system boundaries.
- Write acceptance tests before production implementation.
- Observe the expected test failure before implementing behavior.
- Never delete, weaken, skip, or rewrite a valid test merely to make the suite pass.
- Do not hard-code fixture names or expected fixture outputs in production code.
- Avoid abstractions for hypothetical future features.
- Keep public formats versioned and backward-compatible within a major version.

## Required workflow

1. Read `docs/PRODUCT.md`, `docs/ARCHITECTURE.md`, and the active milestone in full.
2. Inspect existing code and tests before proposing changes.
3. In plan mode, map every step to an acceptance criterion.
4. Stop and report contradictions or missing product decisions.
5. After approval, write tests first and implement the smallest general solution.
6. Run formatting, static analysis, unit tests, and acceptance tests.
7. Report changed files, verification results, limitations, and any newly discovered unknowns.

## Scope of the initial product

- Terraform and OpenTofu plan JSON are the primary infrastructure inputs.
- AWS, Azure, and GCP are supported through provider-specific mappers.
- Object storage is the first vertical resource family.
- The initial interfaces are a local CLI plus JSON and Markdown output.
- MCP, pull-request integrations, live cloud context, dashboards, and deployment are later milestones.

## Definition of trustworthy output

Every finding must include:

- a stable rule identifier;
- severity;
- a concise claim;
- resource address when applicable;
- observed and expected facts;
- evidence locating the source data;
- verification method;
- remediation or a clear explanation of why none is available.

When evidence is insufficient, return `UNKNOWN` rather than `PASS` or `BLOCK`.
